# Measuring harness uplift

**Authoritative experimental methodology, 2026-09-12. PLANNED unless marked IMPLEMENTED.** The purpose is to estimate what the harness contributes while keeping the model and task fixed. It supersedes earlier evaluation/default-promotion rules for new experiments. Historical reports and [thresholds](thresholds.md) remain records of their own conditions.

> **Adopted 2026-09-23, after an external review** ([`external-review-2026-09-23.md`](external-review-2026-09-23.md), backlog R.10).
> The first question this methodology serves: *can the harness raise verified
> success on repository tasks for 7–14B models, at equal model, hardware and
> permissions, and by how much against B0?* The headline is the **absolute
> paired uplift in percentage points against B0** -- not against the bare
> model, which would credit the harness with the tools themselves -- with
> failure reduction as a secondary figure only when B0 fails often enough, and
> per-task paired analysis with intervals over tasks and seeds. No single
> "amplification factor". First campaign: suites A3 and A4 with Qwen3-14B
> under `--arm b0` and `--arm b1`, at least two seeds.

## Current evaluator: useful foundation, incomplete estimand

IMPLEMENTED in `crates/pwr-eval/src/lib.rs`: corpus materialization, visible/hidden verifiers, reference-solution and deliberately-wrong-implementation soundness tests, repeated seeds, structured outcomes, event counts, content-addressed reports/traces, costs and Wilson intervals. CLI build identity records source bytes, including dirty builds. `EvaluationRun` carries provenance alongside `SuiteReport`.

LIMITS verified in source:

- Evaluation supplies the visible verifier; it does not measure normal check discovery or the interactive conversation loop. Call this mode `verifier_supplied`, not product equivalence.
- `measured_outcomes` and the comparison-side construction filter provider failures; headline success/cost can therefore omit unsuccessful starts. Preserve these as explicitly conditional legacy metrics, not primary product reliability.
- `compare` keys by model digest/task ID/seed, without enforcing all task, verifier, backend, sampling, budget and environment identities. Duplicate keys can overwrite previous records through map extension. Same task name does not prove a valid pair.
- Completed task traces are exported, and `pwr eval run` writes per-trial `started` and `outcome` artifacts as each trial crosses those boundaries. Periodic event checkpoints, explicit `--resume`, active markers, retry markers and unfinished-trial export are implemented for campaign durability. Resume retries assigned trials with missing outcomes; it is not semantic replay of a partially executed model turn. A log hash is not a substitute for retained trace bytes and final diff.
- Repository-question scoring is lexical; it does not establish semantic diagnosis. Current corpora include valuable upstream tasks but many supply strong localization hints or saturate on the tested cohorts.

No new benchmark numbers or confidence intervals were generated by this documentation revision.

## Experimental unit and baselines

A trial is one immutable task/workspace/environment, deployment configuration, harness condition, budget and repetition. The central paired contrast changes only the preregistered harness factor. Pair across the same tasks and supported seeds, randomize/counterbalance order, and serialize inference initially to control residency/contention. Repeated seeds are not new independent repositories.

Use three baseline levels:

1. **B0 conventional loop:** same backend, ordinary read/search/edit/command tools, bounded transcript, fixed policy, shared policy enforcement and independent acceptance checks. Do not remove safety or correct protocol handling to make it weak.
2. **B1 existing PWR:** frozen binary/source/config, with its current context and recovery. Separate `verifier_supplied`, scripted product and interactive modes.
3. **B2 strong simple/fixed policy:** development-selected best representation per deployment and a staged localization → repair → validation workflow, motivated by [Agentless](https://arxiv.org/abs/2407.01489). H6 must beat the relevant best fixed control, not only B0.

IMPLEMENTED 2026-09-13 as `pwr eval run --arm b0|b1|b2` (`crates/pwr-orchestrator/src/baseline.rs`). B0 receives the shared instructions and the task, bounds its transcript by dropping the oldest exchanges, runs no check and is finished on its declaration. B2 localizes with read-only actions and names files, repairs with those files shown and no commands, and is validated by the harness for up to three rounds; a question localizes and answers and is accepted only with the workspace unchanged. Both share B1's tool catalog, policy enforcement, reply-fault handling, family adapter and event log. LIMIT: B2 runs one representation for every deployment; the per-deployment selection is not done. The arm is a report condition (`arm`), refused as an undeclared difference like any other. `--oracle-context` is a diagnostic condition (`oracle_context`), not an arm: it prepends the allowed files' contents, which removes localization rather than improving it.

Compare with an external harness only when it can run the same deployment and tasks. Pin its release/commit, tools, prompts, policy and budgets; disclose irreducible differences. Frontier model comparisons are optional reference ceilings, not the primary experiment. A local/frontier × PWR/reference-harness factorial can later estimate interactions, but cloud access and model changes cannot contaminate a same-model claim.

## Trial manifest and lifecycle

PLANNED strict trial identity binds:

- Task statement, task kind, base commit/tree and dirty input snapshot, allowed scope, setup/dependency locks, task artifacts, visible check and hidden acceptance hashes, reference solution/provenance and corpus revision.
- Model artifact/digest, quantization and KV-cache format, backend build, adapter, tokenizer/template where observable, reasoning mode, sampling/seed support, loaded context and output limits. Unknown fields are recorded and constrain the claim; they are not silently equal.
- Hardware identity including accelerator/memory, host probe version, concurrency/residency/offload, pressure/thermal observations, model load and prefix-cache protocol, environment and network policy.
- Source/binary/config hashes, condition ID, permitted treatment differences, all budgets, trial/repetition ID, randomization schedule and stopping rule. Harness revisions may differ only as a declared treatment; all unlisted differences reject causal pairing.

Persist trial allocation before execution, then `started`, active-loop evidence, periodic evidence checkpoints, and one outcome: completed, declined/blocked, timed out, provider/environment failed, interrupted, or infrastructure failure. IMPLEMENTED 2026-09-13: campaign allocation is written as a manifest before execution, and each attempted trial writes immutable `started` and `outcome` artifacts under the campaign's trial artifact directory. The next runner also writes an immutable `active` artifact after the task workspace, run id, budgets and action-loop state are known, so a started trial that has not produced an outcome can be distinguished from a trial that never entered the loop. During an active trial, the evaluator now snapshots the run's SQLite event chain every 30 seconds into immutable `traces/checkpoints/` artifacts; these snapshots are best-effort evidence and never change the task result. `pwr eval run --resume <manifest>` now reloads retained outcomes and attempts only assigned trials with no outcome, after checking that the corpus, harness, deployment, mode, arm, timeout and hardware conditions still match. When a previous active marker exists, resume writes an immutable retry marker before starting the fresh workspace, so the retry is visible rather than silently replacing the lost attempt. `scripts/r2_pilot_status.py` exports every started-without-outcome trial to `unfinished-trials.json`, distinguishing an entered action loop from a trial that never produced an active marker. New manifests also carry the campaign conditions that used to exist only in the final report — harness revision, deployment fingerprint, hardware key, execution profile, mode, arm, oracle-context flag and turn timeout — so a partial campaign can still be attributed to the condition it measured. Do not silently rerun and replace a failure; a retry is another recorded attempt charged to its assigned condition. Preserve original inputs, final diff, baseline/final checks and raw events before temporary workspaces are removed. Unknown schema versions must not disappear from campaign accounting.

The comparator rejects duplicate trial keys and incompatible undeclared differences. Missing pairs are reported with their cause; report all assigned outcomes as well as the matched sensitivity analysis. A report cannot call a campaign complete while scheduled trials are absent.

## Outcomes and denominators

Primary estimand: **all-assigned-trial verified completion at a fixed wall-time and aggregate resource budget**, counting provider failures, timeouts, interrupted/unfinished work and failed candidates. Legitimate task refusal has a task-specific rubric and cannot count as success on ordinary coding tasks. Report administrative interruption separately; it stays missing/unsuccessful in the primary conservative result until resolved by the preregistered protocol, never disappears.

Also report conditional model-served completion, task-success evidence strength, and success-conditioned cost as secondary views. If no model ran, generated tokens may be known zero; if counters are missing, they are unknown. A cost total with missing counters carries coverage and cannot claim complete resource accounting. Record wall time even for failed starts.

| Dimension | Definition / evidence |
|---|---|
| Task success | Independent task-appropriate acceptance; repair requires intended regression fixed and agreed baseline; feature requires stated behavior, not only compilation. |
| False acceptance | Agent/runtime says accepted but hidden checks or task rubric fail. Separate “checks passed” from complete natural-language success. |
| Tool reliability | Parse-valid / schema-valid / semantically appropriate / executed / effect-verified rates, each with its own denominator. Wrong-but-valid calls count separately. |
| Work and cost | All inference calls/turns, prompt/generated/reasoning tokens where reported, underlying tool operations, retries, probes, worker calls and integration. Batches count constituent operations. |
| Time | Observed end-to-end elapsed time including failed starts and admission/probe/load under the declared cold or amortized protocol; report the budget cap separately, with prefill, decode, tool/check and idle time where instrumented. Timeout-censored latency is labeled. |
| Resources | Peak host/backend/process memory where attributable, accelerator memory where available, pressure/offload/cache observations, storage/index cost. Apple unified memory must not be double-counted as separate RAM and VRAM. |
| Context | Delivered versus requested/estimated tokens, useful evidence recall/precision on annotated tasks, stale citations, repeated unchanged reads, rehydrations and loss after compaction. |
| Recovery | Verified completion after an injected failure, repeat-action/loop rate, false-stop rate, extra cost and resume correctness. |
| Human interaction | Required interventions/approvals, redirects, unattended completion and time waiting for input. Freeze grants across causal arms. |
| Scope/policy | Unauthorized effects attempted/blocked/succeeded and user changes damaged. Zero observed violations is a finite-sample observation. |

Two resource views are required: a wall-time budget with complete compute reporting, and a matched underlying-operation/inference budget. This prevents batching, best-of-N, retries, workers or longer reasoning from “winning” by moving the cost outside the denominator. For recurring use, show cold one-off cost and a preregistered amortized repeated-session cost including calibration invalidation; no arbitrary amortization over infinitely many future tasks.

## Tasks and microbenchmarks

Use existing corpus and real trace fixtures as development/regression data, not newly held-out evidence. Add repository-disjoint confirmation tasks with licenses, upstream versions, task provenance and reference fixes. Public bug fixes may be in training; recent date alone does not prove decontamination. Preserve negative and inconclusive outcomes. [SWE-bench](https://www.swebench.com/) is a useful reproducible external coding benchmark, not a substitute for local context, interaction and recovery tests. Report subset/environment deviations and do not compare to a published leaderboard under different conditions.

| Microbenchmark | Controlled stressor | What distinguishes success |
|---|---|---|
| Tool protocol | Native/JSON, catalog sizes, argument types, dependent calls, correct abstention | Correct canonical intent and effect, not merely parsed JSON. |
| Path/localization | Wrong path, misleading filename, definition versus comment, implementation behind imports | Locate actual evidence; no filename-based answer giveaway. |
| Editing | Stale hash, duplicate match, failed hunk, external edit between read/write | Refuse ambiguous edit, preserve bytes, recover without unauthorized overwrite. |
| Output processing | Large logs, Unicode/escaping, crucial middle or tail diagnostic, truncation | Preserve essential fields and retrieve omitted evidence when required. |
| Context/state | Occupancy/position sweeps, multiple facts, contradictory updates, several compactions | Latest constraints and relevant file versions reach a correct later decision. |
| Failure recovery | Compiler ambiguity, flake, timeout, dropped stream, no-progress cycle | Appropriate repair or named stop; no code edits for an unrelated environment fault. |
| Restart/steering | Kill before/after an effect receipt, redirect mid-task, change branch/model | Reconcile state; no duplicate destructive operation or lost user constraint. |
| Multimodal, later | Screenshot defect, crop/resolution change, text-only deployment | Correct supported observation and verified UI fix; honest unsupported result otherwise. |

End-to-end tasks cover diagnosis, bug repair, new features, multi-file refactoring/migration, dependency/environment work, frontend/backend/services and documentation. Include at least one long task whose duration and dependency depth exceed a single small context, without measuring difficulty only by file count. Read-only diagnosis uses a blind rubric naming root cause, evidence and scope; two independent raters and adjudication or a validated grader are required for semantic claims. An LLM judge alone is secondary evidence. Documentation uses requested content, source correctness and structural/link checks with limits stated.

Hidden checks stay outside model/tool access until final scoring, in a separate evaluator-owned environment. Setup and verifier commands still need timeout, isolation and artifact bounds. Check baseline/reference solution and deliberately wrong implementations so a vacuous pass cannot enter a campaign. A wrong implementation should be a plausible candidate answer: it must satisfy the visible verifier and fail the hidden verifier. They are held outside the corpus file, in `corpus/wrong/`, for the same reason reference solutions are: neither is ever materialised into a run's workspace, and neither may change `corpus_rev`, so a suite can be made to discriminate better without making its past campaigns incomparable. `pwr check-corpus` runs all six checks over a suite; the corpora that clone public repositories are checked by that command rather than by a hermetic test. Task scope and acceptance must follow from what the agent was told, and the sixth check enforces it: the upstream fix, confined to the task's allowed files and applied to the starting workspace, must pass both verifiers. Checking the fix commit whole had let a task through whose repository test asserted the behaviour the statement asked to change, in a file the task did not allow — no in-scope answer could have passed (2026-09-13, `filenamify-reserved-name-extension`). A hidden test that errors before asserting anything also "fails at start"; only the fix-side checks catch that, which is why they are not optional.

## Attribution and inference

A failure symptom is not a cause. Distinguish transport/schema, semantic action selection, stale/missing evidence, wrong edit despite evidence, environment/check problem, policy constraint, resource exhaustion and unknown. Use deterministic trace replay for harness invariants, oracle-context trials for evidence availability, and oracle-action probes for execution validity. These diagnostic arms are not deployable success claims.

Follow [AI Agents That Matter](https://arxiv.org/abs/2407.01502): predeclare cost, task splits and reproducibility details. Use an independent pilot to estimate variance and size confirmation for the practical effects in H1–H6. Freeze sample size/stopping rule and metrics before viewing holdout outcomes. Do not repeatedly inspect results and stop at significance. Factorial prompt × output tests are needed where a bundled change has competing causes.

Report per-deployment/task-class estimates with paired task/repository-cluster bootstrap intervals or an explicitly specified hierarchical paired model. Bootstrap clusters must preserve treatment/control pairs and nested seeds. Wilson intervals may describe a fixed collection of binary trials, but cannot establish unseen-repository generalization. Report practical effect size and uncertainty; do not infer a difference simply from overlapping/nonoverlapping individual intervals. Preregister primary hypothesis and multiplicity handling for secondary arms; do not select whichever metric happened to improve.

Promotion requires the hypothesis's practical threshold, its uncertainty gate, no observed new scope/policy/false-acceptance violations, and cost within the declared budget. Efficiency gains require the lower completion-difference bound above −3 pp. Inconclusive results do not promote a default. Reject the specified minimum useful effect only when its confidence interval excludes that effect or a preregistered equivalence test supports that conclusion. Nonsignificance alone remains inconclusive; it does not disprove adaptive harnesses.

## First implementation and validation

Build a **strict paired-trial accounting contract** in `pwr-eval`, initially wrapping the existing verifier-supplied path. Add immutable trial identities, duplicate/mismatch rejection and all-attempt totals alongside explicitly labeled conditional legacy metrics. Preserve current artifact readers; add a schema version rather than reinterpret old reports.

Acceptance fixtures must reject duplicate IDs and changed task/verifier/sampling/budget outside declared factors; retain a provider failure and an interrupted trial in denominators; reconcile total elapsed time and available counters to raw trials; and represent unknown counters honestly. This is the first engineering task because otherwise every later adaptation experiment can report misleading uplift. Shared product execution and durable resume follow as separate, evidence-tested migration steps.
