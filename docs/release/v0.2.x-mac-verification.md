## Agent mode: fixed task and observed symptoms

`src/parser.rs` through `read_file`, validate the call against the schema, and
answer `1337` from a supplied tool result. The tests use temperature zero and
seed 7. Full local calibration was rerun with the corrected engine.

## Sandbox and browser

- The sandbox permits reads from `~/.dotnet`, the per-user .NET installation
  used by GitHub's macOS runners. Its first-run test now selects that binary
  when present and has no CI-only skip. The local Mac has a system-wide .NET
  installation, so the per-user executable path still needs runner validation.
- `look_at` resolves a browser symlink to its actual app bundle before granting
  sandbox reads. It also recognizes Chrome for Testing and retains bounded
  browser stderr when screenshot capture fails. The CI-only skip is removed.
  [GitHub's macOS runner inventory](https://github.com/actions/runner-images/blob/main/images/macos/macos-14-Readme.md)
  lists both Chrome variants. Capture passes locally with `CI=1`; runner
  behavior was then checked on the hosted runner (below).

The first `develop` push exposed two remaining runner-only failures in
[CI #30](https://github.com/VitoSanta/PWR/actions/runs/36531031606):
NuGet's first-run migration created `/tmp/.dotnet.XXXXXX` and Seatbelt denied
the directory creation; Chrome stopped at its log path lookup with
`Failed to get the path for 1001`. The sandbox now allows only the named .NET
temporary directory pattern. `look_at` gives Chromium `CFFIXED_USER_HOME`
pointing inside the workspace scratch area, so CoreFoundation resolves its
application-support path there before Chrome applies `--user-data-dir`.
The follow-up [hosted macOS CI run](https://github.com/VitoSanta/PWR/actions/runs/36532042438)
passed every job, including the Rust sandbox tests, desktop build and MLX
sidecar tests.

## Full-screen UI stress test of the installed v0.2.0 DMG

The installed PWR app was put in macOS full screen and tested in Chat mode
with `gpt oss 20b`, without a workspace. One response had 25 numbered lines
(`ALFA-01` to `OMEGA-01`); a second had 100 (`BETA-START` to `BETA-END`).
Both finished, and all four markers remained in the accessibility tree after
switching to another conversation and reopening the test conversation.

Reproduced defect: while viewing the end of the 100-line reply in Detailed
trace mode, selecting Compact jumped the viewport to the first message. The
reply was still present, but the jump could look like a reload or missing
messages. The conversation used a smooth scroll on every streaming update;
that repeatedly animated the viewport as the answer grew. The patched native
bundle follows immediately only while pinned to the bottom and reapplies it
after a trace-view change. Reopening the 100-line reply retained all four
markers and changing Compact → Detailed → Compact kept the viewport at its
end. A second agent-mode 100-line test exposed a subtler regression: scrolling
up temporarily held position, but the viewport jumped to the bottom when the
layout contracted at completion. The scroll handler now repins only after an
actual downward scroll near the bottom; an upward wheel gesture unpins it
immediately. In the repeated test, the first turn stayed visible through the
whole generation and after completion; scrolling down voluntarily reached
`TEST-100`, and switching Compact/Detailed retained the end position.

The two finished turns showed `3s` and `18s` before leaving, then `0s` on
reopening: replayed events have fresh local timestamps. The patched app omits
duration from restored turns, since their actual elapsed time is not saved.

## Agent-mode tool stress test in the patched native app

In macOS full screen, `gpt oss 20b` ran in an isolated test workspace with
`input.txt` containing `alpha=17` and `beta=23`. The task was to write exactly
`TOTAL=40` to `result.txt`, read it back, and leave other files alone. PWR
asked to run `sh` twice; the first was allowed once and the second for the
session. It executed two commands and one file read. `result.txt` held the
exact expected bytes, and no other fixture file changed.

The first patched bundle exposed two new UX defects:

1. The streamed answer was rendered inside the “Implementing” phase, then
   repeated below it when the core appended its independent-check verdict.
   The frontend now replaces the streaming entry with the authoritative final
   answer. A regression test covers the changed final text.
2. Reopening the conversation kept the final model text but silently lost all
   tool actions and the check verdict. The saved snapshot contains structural
   model calls and tool results. Replay now reconstructs each call's name,
   target/command and success state and restores the verdict. The UI labels
   the reconstructed trace and says that detailed output, diffs and timings
   were not saved. Tests cover this replay path. This is a summary, not the
   original live trace; preserving the complete trace remains future work.

The sentence “nothing verified this” was also ambiguous after the agent read
the file back. For workspaces with no declared automated checks, the turn now
says “Independent verification unavailable: this workspace declares no
automated checks.” This distinguishes the app's independent checks from
inspection performed by the model.

A second GPT OSS turn wrote `check.txt` with exactly `CHECK=40`, read both
`result.txt` and `check.txt`, and finished with a single answer. Reopening the
conversation showed a restored summary of its one edit and two reads. A
third turn produced `TEST-001` through `TEST-100` without tools; all markers
survived the scroll and trace-view stress test.

Switching the selected model to Gemma 4 exposed incorrect attribution: every
older PWR turn header changed from GPT OSS to Gemma 4. New live turns now
capture their model label at send time. On replay, PWR recovers each turn's
model from the append-only `generation.started` audit beside the saved
snapshots. If rewind or compaction changes the visible history so that an
identity cannot be matched safely, it shows `model not saved` for that turn.
The final native bundle was reopened with GPT OSS and Gemma 4 turns in one
conversation; all five restored headers showed the right, readable model
names even though Gemma 4 was currently selected.

Gemma 4 used `read_file` successfully on `check.txt`, but its final answer
included internal reasoning and a literal `<channel|>` marker before
`CHECK=40`. The model sometimes starts its reply inside a thought channel
opened by the prompt, so only the closing marker appears in generated text.
The Gemma adapter now moves the prefix into the thinking channel and keeps
only the suffix as the answer. Its revision is `gemma4-v2` and the suite is
now `quick-calibration-5`, which invalidates evidence from the earlier parser.
Gemma's raw content chunks are also withheld from
the live answer rail until the adapter has classified them, since the same
unmarked thought text otherwise flashes in the UI while streaming. The fixed
task was repeated in the native app: Gemma called `read_file` once and the
final answer was exactly `CHECK=40`. In the suite-5 bundle, GPT OSS's old
result was shown as stale; a fresh Quick Calibration passed and restored
`Locally calibrated`. Gemma also passed the eight suite-5 checks and returned
to `Locally calibrated`, with tool calling and structured output supported.

The final full-screen bundle ran one more Gemma turn without tools. While it
generated, the UI showed a working state and no raw thought or control token;
the final answer was exactly `PRONTO`. That uncovered a timer regression:
without streamed answer chunks, the completed turn initially showed `0s`.
The turn now uses the preceding user message as its start time, and the
working placeholder shows elapsed time even before the first visible output.
In a fresh native conversation the placeholder advanced from `0s` to `48s`;
Gemma finished with `PRONTO` and the completed turn showed `1m 14s`.

## Top-bar panels closing in the native app

Reproduced in the native bundle built from `1fd6c661`: a top-bar panel
(Context, Runtime metrics, Tools, …) stayed open after a click outside the
window -- on another app or the desktop -- and was still open on returning to
PWR. Clicks inside the window (conversation, title strip, composer, another
bar control) already closed it, and opening another panel replaced it.

`pa-popover` now also closes when the window loses focus, and hears the press
in the capture phase as both a pointer and a mouse event, so nothing on the
page can stop it first. Checked in a fresh native bundle with real clicks:
Context closed after a click on the desktop; the title strip, the composer
and switching between Runtime metrics, Tools and Context still behave as
before, and a click inside an open panel leaves it open. Desktop unit tests
(85) and the production build pass.
